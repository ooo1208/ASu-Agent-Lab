# 本地运行、可选 Docker 与自动检查

本项目提供两种运行方式：`demo` 使用本地合成业务与真实的 SQLite 文档/评估服务，不调用大模型；`live` 启动继承并改造的 DeepAgents/MCP/OpenSandbox 链路，需要另外配置模型、MongoDB 和沙箱。默认选择 `demo`。

Docker 配置是可选部署入口。本次实现环境没有可用 Docker 引擎，未宣称完成镜像构建、容器运行或完整 live 端到端验收。

## 1. 安装一次，再启动

建议 Python 3.11、Node.js 22.12 或更高的 22.x、Java 21、Maven 3.9 和 uv 0.11.2。Python 和前端依赖按锁文件安装；启动器不会自动安装依赖、运行 Maven 构建或下载模型。

在仓库根目录执行：

```powershell
uv sync --locked
Set-Location frontend
npm ci
Set-Location ..

# 需要采购写入演示时先构建 Java 服务
mvn -f erp-service/pom.xml package
```

Windows：

```powershell
.venv/Scripts/python.exe start_all.py --check
.venv/Scripts/python.exe start_all.py --erp
```

Linux/macOS：

```bash
.venv/bin/python start_all.py --check
.venv/bin/python start_all.py --erp
```

`--erp` 只启动已经构建好的 `erp-service/target/erp-service-1.0.0.jar`。不加此选项也能使用文档检索和本地评估；批准采购演示时则需要你已经在 `ERP_API_BASE_URL` 指向的地址运行了 ERP。

默认访问：

| 地址 | 服务 |
|---|---|
| `http://127.0.0.1:5173` | Vue 前端，开发服务器代理 `/api` 到 8090 |
| `http://127.0.0.1:8090/docs` | FastAPI 接口文档 |
| `http://127.0.0.1:8090/health` | API 存活检查 |
| `http://127.0.0.1:8080/actuator/health` | 可选 Java ERP 健康检查 |

## 2. 统一启动器的行为

`start_all.py` 启动前检查依赖、配置和监听端口；按顺序拉起服务并等待可检查的服务就绪。任一子进程意外退出时，启动器停止自己拉起的其他服务，避免出现前端可见但业务进程已经消失的假正常状态。

日志位于 `ASU_DATA_DIR/logs/`，默认 `.local/asu/logs/`。Web 与 Worker 共用 `ASU_DATA_DIR/evaluation.sqlite3`。停止进程不会删除数据库。按 Ctrl+C 停止启动器管理的进程树；Windows 子进程以隐藏窗口启动，并通过受控 PID 的进程树清理回收，不弹出多个命令行窗口。

```powershell
# API + 独立 Worker，不启动前端
.venv/Scripts/python.exe start_all.py --no-frontend

# 只预检，不启动任何服务
.venv/Scripts/python.exe start_all.py --erp --check

# 就绪后运行 3 秒，随后清理自己启动的进程，用于本机短验收
.venv/Scripts/python.exe start_all.py --no-frontend --stop-after 3

# 可选报价页面服务，默认端口 8086
.venv/Scripts/python.exe start_all.py --erp --quotes
```

其他参数：`--python` 指定已有 Python、`--erp-jar` 指定已有 jar、`--no-worker` 不启动 Worker、`--frontend-port` 修改前端端口、`--api-port` 修改 API 端口并同步前端代理地址、`--protocol-port` 修改 live 异步服务端口、`--wait-timeout` 设置启动等待时间。端口占用时会报错，不会终止用户已经运行的进程。

启动器读取仓库根目录 `.env`，已有环境变量优先。使用项目 `.venv` 运行可确保 `python-dotenv` 可用。请从 `.env.example` 填写所需设置；不要提交本地 `.env`、API key、数据库或测试账号数据。

## 3. 本地演示闭环

1. 打开前端注册一个本地测试用户。
2. 在证据工作台导入自己准备的合成 TXT/Markdown/CSV/可提取文字的 PDF。
3. 在聊天页输入文档关键词，返回当前用户的检索片段及引用。此模式明确不调用大模型。
4. 输入“演示下单 2 件”，先看到待审批操作；拒绝不会调用 ERP 写接口，批准才发送带幂等 key 的创建请求。
5. 在评估中心查看完成快照、Worker 评分和本地待投递事件。
6. 提交人工反馈与修正后的期望，显式加入新版本黄金集，再以该数据集采集和比较候选输出。

订单执行结果未知时，先核对 ERP 状态。演示流程会记录 `outcome_unknown`，不会自动重放该写操作。上下文里程碑中出现“approved”等文字或字段不会授予审批权限。

## 4. 独立评估与 Langfuse

默认 Worker 仅在本地评分，不会因为设置了 Langfuse key 就自行联网。

```powershell
python -m asu_eval.seed --db .local/asu/evaluation.sqlite3
python -m asu_eval.worker --db .local/asu/evaluation.sqlite3 --once

# 显式选择远端投递；先设置 LANGFUSE_HOST/PUBLIC_KEY/SECRET_KEY
.venv/Scripts/python.exe start_all.py --delivery langfuse
```

远端模式会发送已采集的输入、结构化输出、用户/会话标识和分数，应按实际数据要求先脱敏。详细输入契约、版本门禁、租约恢复与远端传递语义见 [evaluation.md](evaluation.md)。没有真实 Langfuse 凭据时，不能将本地测试称为远端上线验收。

## 5. 可选 Docker 合成演示

需要 Docker Engine/ Docker Desktop 与 Docker Compose v2。以下命令从仓库根目录运行：

```powershell
docker compose -f docker/compose.demo.yml config
docker compose -f docker/compose.demo.yml up --build -d
docker compose -f docker/compose.demo.yml ps
docker compose -f docker/compose.demo.yml logs -f demo-api worker
```

编排包含 Java ERP、FastAPI demo、独立评估 Worker 和 Nginx 静态前端。前端端口仍为 5173，API 为 8090；宿主机监听只绑定 `127.0.0.1`。ERP 和评估数据分别持久化到 `erp-data`、`asu-data` 命名卷。API 与 Worker 挂载同一个评估卷，默认 Worker 不连接 Langfuse。

Nginx 对 `/api` 关闭响应缓冲，以支持 SSE；生产式外部访问应另外配置 TLS、访问入口和相应应用设置。本 Compose 是本地演示部署，没有宣称具备生产高可用和多机 SQLite 能力。

停止并保留数据：

```powershell
docker compose -f docker/compose.demo.yml down
```

不要随意追加 `-v`；那会删除命名卷中的本地演示数据。

Python 镜像使用项目锁文件构建，前端使用 `npm ci`。各 Dockerfile 的专用 ignore 文件排除了宿主 `.venv`、`.env`、数据库和构建缓存，避免把本地运行状态装进镜像。[Docker 构建上下文规则](https://docs.docker.com/build/concepts/context/)、[uv Docker 集成](https://docs.astral.sh/uv/guides/integration/docker/)。

## 6. live 模式的额外基础设施

`live` 不会自动启动 Docker。可先单独启动 `docker/compose.live-infra.yml` 中的 MongoDB 和 OpenSandbox，然后在宿主机运行 Python Agent。

```powershell
docker compose -f docker/compose.live-infra.yml up --build -d
```

需要核对的设置：

| 设置 | 用途 |
|---|---|
| `DEEPSEEK_API_KEY` / `DEEPSEEK_BASE_URL` | 实际模型接口 |
| `JWT_SECRET_KEY` | 至少 32 字符的随机认证密钥 |
| `MONGODB_URI` | 本地示例为 `mongodb://127.0.0.1:27017`，数据库 `asu_agent`；若使用其他已认证服务，配置对应凭据 |
| `OPENSANDBOX_URL` | 宿主机通常为 `http://127.0.0.1:8100` |
| `OPENSANDBOX_API_KEY` | 采用已配置鉴权的服务时填写 |
| `ERP_API_BASE_URL` / `ERP_API_KEY` | 业务 REST 地址和可选应用 key |
| `ERP_MCP_URL` | 启动器所启用的本机 MCP，默认 `http://127.0.0.1:8000/mcp` |
| `ASYNC_AGENT_PROTOCOL_URL` | 启动器拉起的异步 Agent Protocol，默认 `http://127.0.0.1:2024` |

```powershell
.venv/Scripts/python.exe start_all.py --mode live --erp
```

live 启动器会额外启动 `python -m mcp_server.server_main` 和 `python -m langgraph_cli dev --host 127.0.0.1 --port 2024 --no-browser --no-reload --allow-blocking`，等待协议服务 `/ok` 就绪，再启动 `api_view.web_main:app`。Agent Protocol 是异步子 Agent 的实际执行服务，不能省略。继承的 OpenSandbox 本地配置需要正在运行的 Docker daemon、挂载 Docker socket，并使用只绑定本机端口的开发模式；不要直接把该服务暴露到公网。沙箱镜像 `asu-agent-sandbox:v1` 和宿主 Docker 网络必须实际验证，服务启动成功本身不等于完整工具链已经验收。

报价页面：`--quotes` 启动 `mcp_server.quote_server`，`QUOTE_HOST`/`QUOTE_PORT` 控制监听，`QUOTE_BASE_URL` 用于页面地址映射。沙箱内的 `localhost` 指向沙箱自身，若需要从 Docker 沙箱访问宿主报价服务，应使用沙箱可达的宿主地址，例如 Docker Desktop 的 `host.docker.internal:8086`，并在本机受控网络范围内配置可访问监听。启动器不会自行修改和同步 Skills；使用报价服务提供的映射命令后还需同步沙箱内 Skills。

## 7. CI 做了什么

`.github/workflows/quality.yml` 包含三个独立任务：

- Python 3.11：`uv sync --locked`、本地 pytest、正确夹具门禁，以及断言故意回归夹具退出码为 1。
- Node.js 22：`npm ci`、生产构建、`npm audit --audit-level=high`。依赖新增高危公告时该任务会失败，需要实际审查和更新锁文件。
- Java 21：`mvn test`，运行合成业务与事务测试。

默认 pytest 排除显式标记的 `integration` 与 `live` 测试，避免在没有外部服务或模型 key 的环境中假装执行在线验收。新增 `tests/lab/` 使用真实 FastAPI TestClient、临时 SQLite、真实内存 MCP Client 与受控 HTTP transport，对注册登录、隔离、审批和观测等逻辑执行本地集成测试。

GitHub Actions 的首次远端结果以仓库 Actions 页面为准；写入工作流文件不等于已经通过远端运行。
